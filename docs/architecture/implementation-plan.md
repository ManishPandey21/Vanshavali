# Implementation Plan — Vanshavali (Indian Family Heritage Platform)

Status: living document. Authoritative product input:
`Indian_Ancestry_Family_Heritage_Platform_Requirements.md` (PRS v1.0, 24 Sep 2026; summarised in
[`docs/requirements-traceability.md`](../requirements-traceability.md)).

Legend used throughout: **ASSUMPTION** = documented choice, work continues · **DEFERRED** =
intentionally postponed, with the phase named · **BLOCKER** = cannot proceed safely without owner input.

## 1. Repository assessment (discovery, 25 Sep 2026)

| Area | Finding |
|---|---|
| Shape | Partially initialised. A single Vite 6 + React 18 + TypeScript + Tailwind 4 SPA at the repo root. |
| Data | All in-memory (`src/data/sampleData.ts`) plus master vocabularies (`src/data/masterData/*`: gotras, kulas, nakshatras, rashis). |
| Backend / DB / auth | None. |
| Tests / lint / CI / Docker / deploy | None. |
| Package manager | npm (`package-lock.json`). |
| Domain model | `Person` has `fatherId/motherId/spouseIds/childrenIds`, stored in both directions and drifting apart. Gender is binary. Living people are public by default (see `docs/architecture/README.md` F1–F9). |
| Reusable | Visual language (amber/heritage palette, lucide icons), master vocabularies (used **only as suggestion lists**, never to infer), the page ideas (dashboard, tree, members, gotra view). |
| Not reusable as-is | The data model and the fixed parent columns. The `BiodataGenerator` (matrimonial biodata is P2 / out of MVP scope, and it bundles family data without consent). |

**Decision:** the SPA is kept as a starting point, not replaced wholesale. It moves to `frontend/`,
gets a real API client, routing and tests, and its prototype components are rewritten against the
API. The mock-data-only screens are removed as their real counterparts land.

## 2. Chosen architecture

A **modular monolith** ([ADR-0001](adr/0001-application-architecture.md)):

```
frontend/  React SPA (Vite, React Router, TanStack Query, i18next) → talks only to /api/v1
backend/   FastAPI app, one deployable, split into domain modules; RQ worker (same codebase)
           for scanning, OCR, extraction, GEDCOM import/export
infra      PostgreSQL 16 · Redis 7 · S3-compatible object storage (MinIO locally) · ClamAV (clamd)
e2e/       Playwright tests that drive the real frontend against the real backend
```

No Kubernetes, Kafka, Neo4j, CQRS, event sourcing, microservices or second search engine on day 1.
Each is listed in §12 with the measurement that would justify adding it.

## 4. Domain boundaries (backend modules)

```
identity      users, sessions, password hashing, CSRF, rate limiting
trees         trees, memberships, roles, invitations, tree settings (public mode)
authz         permission matrix, privacy evaluation, field redaction (no routes; used by all modules)
genealogy     persons, name records, relationships, relationship engine, ancestry traversal
events        vital/life events (birth, death, marriage, migration…), genealogical dates, places
heritage      assertions (gotra, pravara, kula…), heritage profiles for persons and branches
family        households, family branches, memberships
evidence      sources, citations, evidence status, provenance, conflicts
documents     vault: upload, validation, scan, storage, previews, links, download URLs
extraction    OCR engines, extractors, proposals, review → confirmed facts
astrology     astrology profiles, Kundli conflict detection
property      properties, land parcels, interests, property events, timeline
gedcom        GEDCOM 7 import (staging, report, duplicate preview, commit) and export
search        people/place/document/property search, duplicate candidates
privacy       consent records, profile claims, public tree read models
audit         append-only audit log
```

Dependency rule: modules depend on `core`, `authz` and the shared models. Routers never touch
another module's tables directly, only its service functions.

## 5. Database strategy
- PostgreSQL is the **only** canonical store ([ADR-0002](adr/0002-database-choice.md)).
- **Tree = tenant.** Every tree-scoped table has `tree_id NOT NULL`, indexed. Cross-entity foreign
  keys are **composite `(tree_id, id)`**, so a relationship, citation or interest can't point into
  another tree even through a bug.
- IDs are UUIDv7 (time-ordered, can't be enumerated).
- Genealogical dates are stored as structured JSONB (`calendar, precision, year, month, day, end…,
  original_text`) plus derived `sort_from`/`sort_to` DATE columns for ordering and range queries. No
  invented day or month ([ADR-0003](adr/0003-genealogy-relationship-model.md)).
- Alembic migrations only. The migration test runs `upgrade head` on an empty DB, then `alembic
  check` (models = migrations), then `downgrade base`, then `upgrade head`.
- The audit table is append-only: a trigger rejects UPDATE and DELETE.
- **DEFERRED (Phase 8):** Postgres RLS as a second isolation barrier. Composite FKs plus the
  tree-scoped service layer plus isolation tests are the MVP control.

## 6. Document storage strategy
Pipeline: `upload → size/type validation (magic bytes) → SHA-256 → malware scan → encrypted,
content-addressed, write-once object → preview → OCR → extraction proposals → human review →
confirmed facts + citation + provenance` ([ADR-0004](adr/0004-document-storage.md),
[ADR-0009](adr/0009-ocr-ai-provenance.md)).
- There are two storage classes, **STANDARD** and **VAULT** (birth certificates, wills, deeds,
  land and identity records). Each has its own data key and key prefix.
- Originals are never overwritten. Metadata edits are versioned. Deletion is a soft delete plus a
  retention policy, and deleted documents can be restored.
- Downloads use a short-lived (≤300 s) signed URL, issued only after authorisation. Every issue is
  audited.

## 7. Authentication strategy
[ADR-0005](adr/0005-authentication.md): email + password (Argon2id), and a server-side session
table storing only a SHA-256 of the token. Cookie `vsh_session` is HttpOnly, SameSite=Lax, and
Secure in production. The CSRF double-submit token (`vsh_csrf` cookie + `X-CSRF-Token` header) is
required on every unsafe method. Sessions can be revoked (logout, logout-all). Login is
rate-limited. **DEFERRED (Phase 8):** TOTP MFA, email verification and password reset, which need
an email provider (**ASSUMPTION:** dev uses a console outbox).

## 8. Authorisation strategy
[ADR-0006](adr/0006-authorization.md): deny by default, with one policy module (`app/authz`).
- Roles per tree membership: `OWNER, FAMILY_ADMIN, BRANCH_ADMIN, CONTRIBUTOR, RESEARCHER, VIEWER,
  DOCUMENT_CUSTODIAN, PROPERTY_CUSTODIAN`. `SYSTEM_ADMIN` is a platform flag and gives **no**
  access to tree content.
- A permission matrix maps roles to actions. Branch-scoped roles apply only to people in their
  branch.
- Privacy levels (PRS §6): `PRIVATE_SELF, PRIVATE_TREE_ADMINS, FAMILY_BRANCH, TREE_MEMBERS,
  INVITED_RESEARCHER, PUBLIC_DECEASED_ONLY, CUSTOM`. They apply per object (person, document,
  property, assertion, astrology profile) and per field, with overrides on the person.
- Living, unknown-status and minor people get stricter field defaults (full DOB, birth time,
  address and contact are admin-only), and **never** appear in public read models.
- A resource from another tree returns **404**, not 403, so its existence isn't revealed.

## 9. Graph / traversal approach
The relationship table holds typed edges (`person_a` → `person_b`, type, lineage, union, dates,
evidence). Ancestor and descendant queries use **recursive CTEs** with depth limits and cycle
guards, indexed on `(tree_id, person_b, type)` and `(tree_id, person_a, type)`. The relationship
calculator (cousin degree and removal, in-laws, step and adoptive) loads the tree's edge list once
per request (10k people ≈ 30k edges ≈ a few MB) and runs BFS / lowest-common-ancestor in Python.
**DEFERRED:** a closure table or materialised paths. They get added only if the p95 targets (PRS
§49) fail in Phase 8 load tests. Neo4j is not planned.

## 10. Search strategy
[ADR-0007](adr/0007-search.md): each `NameRecord` stores `search_text` (a lowercase, accent-folded
ASCII romanisation, where Indic scripts are transliterated with `indic-transliteration`) and
`search_phonetic` (a metaphone key per token). Queries run exact → prefix → trigram → phonetic,
and every result carries a **match reason**. Results pass through the same privacy filter as the
API. **DEFERRED:** OpenSearch or Meilisearch, which only become worth it at more than about 1M
names or for cross-tree discovery.

## 11. Phase plan

The spec's phases are reordered slightly. GEDCOM export moves forward so data is portable early,
and the documents pipeline comes before astrology because Kundli upload reuses it.

| Phase | Scope | Exit criteria |
|---|---|---|
| **0 Foundation** | Monorepo layout, backend skeleton, config, DB, Alembic, auth, trees, memberships, authz core, audit, Docker compose, CI, test harness, frontend move and API client | Backend and frontend start. Migrations round-trip. Auth and isolation tests pass. |
| **1 Core genealogy MVP** | Persons, names, events (birth with time precision, death, marriage), places (historical names), relationships (all types, unions, multiple spouses), sources and citations, evidence status, privacy (living, minor, field-level), invitations, tree/ancestor/descendant views, relationship calculator, search v1 | Playwright flow 1 and viewer-denial flow 4 pass |
| **2 Indian family model** | Heritage assertions and profiles (person and branch), households, branches, ancestral village, migration events, multilingual names/UI (en and hi) | Heritage "no inference" tests and household/branch APIs and UI pass |
| **3 Documents & evidence** | Vault, validation, scan, encryption, previews, signed downloads, links, OCR, birth-certificate extraction, review → facts, conflict view | Playwright flow 2 passes. Document authz tests pass. |
| **4 Astrology** | Astrology profiles, Kundli upload and extraction, conflict review against civil records | Kundli-vs-certificate conflict test passes |
| **5 Ancestral property** | Property, parcels (extensible identifiers), interests (rational shares), events (partition and others), documents, timeline, lineage view | Playwright flow 3 passes |
| **6 GEDCOM** | GEDCOM 7 export with `SCHMA` extension URIs, import staging, report, duplicate preview, confirm, extension preservation | Round-trip test passes |
| **7 Search & discovery** | Transliteration and phonetic search across types, duplicate candidates, merge (reversible) | Search match-reason tests pass |
| **8 Hardening** | RLS, MFA, rate limits via Redis, security headers audit, load tests (10k people), accessibility audit, backup/restore runbook, observability, deployment | Definition of Done |

MVP = phases 0–3 plus the P0 items of 5 and 6 (PRS §57 P0). Post-MVP = the P1 and P2 lists
(§57), tracked in `IMPLEMENTATION_STATUS.md`.

## 12. Deployment approach
- Docker images: `backend` (serves `uvicorn app.main:app`; the worker runs `rq worker` from the
  same image) and `frontend` (static build on nginx, which proxies `/api` to the backend).
- `docker-compose.yml` for local development: postgres, redis, minio, clamav, backend, worker,
  frontend.
- Production target (**ASSUMPTION**, Q12): one managed Postgres with PITR, managed Redis, S3 with
  SSE-KMS and versioning, and containers on a single orchestrator (ECS, Cloud Run or a VM with
  compose) in an Indian region. Migrations run as a release step.
- **Horizontal scale path:** stateless API replicas behind a load balancer, plus more workers.
  Nothing in the design pins state to one process.

### Things that would justify more complexity later
| Technology | Trigger |
|---|---|
| Graph DB | Relationship queries miss p95 < 500 ms at 10k–100k people even after closure tables |
| OpenSearch | Cross-tree discovery or >1M names with fuzzy search p95 > 500 ms |
| Kafka / event bus | More than one independently deployed consumer of domain events |
| Kubernetes | More than ~5 services, or autoscaling needs a single VM/ECS can't meet |

## 13. Major assumptions
1. **ASSUMPTION:** a Vite SPA, not Next.js (ADR-0001). Reversible, because the API is
   framework-agnostic.
2. **ASSUMPTION:** invite-only trees. Public view is opt-in per tree and shows only deceased
   people who have been marked public.
3. **ASSUMPTION:** English and Hindi UI in Phase 2. Names can be in any script from day 1.
4. **ASSUMPTION:** no external AI or OCR providers. Tesseract runs locally. External providers
   need a per-tree opt-in and an ADR amendment.
5. **ASSUMPTION:** the GEDCOM extension URI base is `https://vanshavali.app/gedcom/ext/v1/` until
   the owner registers a domain (ADR-0008). It's configurable.
6. **ASSUMPTION:** email sending is a console/outbox adapter. Invitations return the link to the
   inviting admin.
7. **ASSUMPTION:** Aadhaar numbers are never stored. The extractor masks 12-digit
   Aadhaar-shaped numbers.
8. **DEFERRED:** astrological *calculation* (ephemeris). Values are entered, extracted or
   imported, with provenance recorded. The `calculated` provenance is supported by the schema.

## 14. Technical risks

| Risk | Mitigation |
|---|---|
| Privacy leaks through a new endpoint | All person/document/property serialisation goes through `authz.redact`. Every response schema has a privacy test. Negative tests cover public, search and export. |
| Cross-tree access bugs (IDOR) | Composite FKs, tree-scoped lookup helpers that always take `tree_id`, and a parametrised isolation test over all routes |
| OCR quality on Indic, handwritten and low-quality scans | Results are proposals only. The engine abstraction allows better engines later. Confidence is shown and edit-before-accept is supported. |
| Tree rendering at 10k+ people | Progressive loading from the API (depth-limited ancestors/descendants), virtualised lists, collapsible generations. Benchmark in Phase 8. |
| GEDCOM variation (5.5.1 exports from MyHeritage/Ancestry) | Tolerant parser, preserved raw extensions, an import report with warnings, and a staging area plus confirmation before commit |
| Share arithmetic errors in property | Exact `Fraction` arithmetic, the rule that shares sum to ≤ 1 per property enforced in the service, tested |
| Scope size | The phase gates above, plus `IMPLEMENTATION_STATUS.md` kept honest (only `VERIFIED` once tests pass) |
| Sandbox limitations (no Docker daemon or ClamAV signatures in the CI sandbox) | Compose is validated in GitHub Actions. clamd runs in compose. Tests use an explicit EICAR test scanner. |
