# Accessibility audit, September 2026 (Phase 8)

**Standard:** WCAG 2.2 Level AA (PRS §50): keyboard-accessible family navigation, a non-visual text
representation of relationships, readable chart alternatives, sufficient contrast, screen-reader
labels, and language/script metadata.
**Scope:** the SPA (`frontend/`) against the real API, in English and Hindi, on desktop and on phone
viewports.
**Result:** 17 findings, all fixed. Each fix has a regression check in `e2e/tests/a11y.spec.ts`.
axe-core reports **0 violations of any impact on 83 page states**. The assistive-technology pass
with a real screen reader is still to do (see [Still manual](#still-manual)).

## Method

| Layer | What it covers | How |
|---|---|---|
| Automated rules | Everything axe can decide: names, roles, labels, ARIA validity, colour contrast of text, `lang`, landmarks, tables, target size (2.5.8), and so on | `@axe-core/playwright` 4.13 (axe-core 4.13.0) with the tags `wcag2a wcag2aa wcag21a wcag21aa wcag22a wcag22aa`. Any **serious or critical** violation fails the build. Moderate and minor violations are recorded as test annotations (there are none today). **No rules are disabled or excluded.** |
| Heading outline | One `h1` per page, no skipped levels in `<main>` (1.3.1, 2.4.6) | A custom check on every scanned page, because axe's `heading-order` is a best-practice rule outside the WCAG tags |
| Keyboard-only scripts | Tab order, visible focus at every stop, skip link, focus after navigation, tabs model, dialog trap, Escape and focus restore, focus on the first invalid field, tree arrow-key navigation, no keyboard trap, combobox | Playwright `keyboard.press` only (no clicks), asserting `document.activeElement` and its computed outline |
| Screen-reader semantics | Live regions for async results, `lang` on other-script names, `aria-describedby` on errors, table captions and headers, alt text, status given in words | DOM and accessibility-tree assertions |
| Adaptation | Reflow at 320 CSS px (= 400 % zoom of 1280 px) and 640 px (= 200 %); reduced motion; focus not obscured under the fixed mobile navigation; non-text contrast of input borders | Viewport and media emulation, computed styles |
| Expert review | Everything the tools cannot see: colour-only cues, pointer alternatives, target size inside SVG, focus races, contrast where axe returns "needs review" | Code reading of every component in `src/components` and `src/pages/tree`, plus contrast computed by formula |

The data is seeded through the API: a tree with a living person who has a Devanagari name, deceased
parents published to the public tree, a spouse and a child, a PDF and a photo document, and an
ancestral property with a parcel, a holder and an inheritance event. Browser: Chromium (Playwright
1.56.1).

## Findings and fixes

Severity uses axe's impact scale, judged by effect on users: **critical** blocks a task,
**serious** makes a task very difficult, **moderate** causes friction, **minor** is an irritant.
The automated scan of the existing pages found no serious or critical rule violations: the app was
built with labels, landmarks, ARIA tabs, an accessible dialog and a list alternative to the chart.
All the findings below came from the scripted keyboard and semantics checks and the expert review.

### Contrast items axe could not decide ("needs review")

axe marks colour contrast as "needs review" when it cannot determine the background. Here that
happens for sidebar links clipped by the scrolling sidebar, and for text on the profile header's
white → `kumkum-50` gradient. The pairs were computed by formula:

| Pair | Ratio |
|---|---|
| ink #231a12 on white / on kumkum-50 | 17.1 / 15.7 |
| ink-muted #5c4b3b on parchment / parchment-deep / kumkum-50 | 7.8 / 7.0 / 7.6 |
| kumkum-800 links on white / kumkum-50 | 9.4 / 8.6 |
| active nav kumkum-900 on kumkum-100 | 10.3 |
| haldi-700 on haldi-100 (saffron badges) | 5.2 |
| leaf-700 on leaf-50 (green badges) | 6.5 |
| white on kumkum-700 (primary buttons) | 7.3 |
| focus ring kumkum-700 on parchment (non-text) | 6.8 |
| chart status bars: living / deceased / unknown outline (non-text) | 7.1 / 6.4 / 4.2 |

All pass AA; most pass AAA.

## Pages owned by the concurrent authentication work

These files were being changed by another engineer during the audit, so they were **reported, not
edited**: `pages/auth/*`, `pages/AccountPage.tsx`, `api/*`, auth i18n keys, and routing. They are
in the axe scan and pass it with 0 violations.

- **R1 (moderate, 2.4.3): FIXED at integration.** After submitting Register, the form was
  replaced by "Check your email" and focus fell to `<body>`. `AuthFrame` now takes `focusHeading`,
  which moves focus to the new `h1`. Regression test: `EmailAuth.test.tsx` ("shows a
  check-your-email state…"), which fails without the fix.
- **R2 (minor, 3.3.1):** login and register rely on native `required` validation bubbles on an
  empty submit. These are accessible, but they differ from the rest of the app's `aria-invalid` +
  `aria-describedby` pattern. Consider `noValidate` plus the shared `Field` error wiring.

## Still manual

- **Screen-reader pass (recommended before release).** This could not be run here. Use NVDA +
  Firefox and JAWS + Chrome on Windows, VoiceOver + Safari on macOS and iOS, and TalkBack + Chrome
  on Android. Scenarios:
  1. register, create a tree, add a person with a Devanagari name;
  2. add parents, a spouse and a child through the dialogs;
  3. explore the tree chart with arrow keys, then the list view;
  4. relationship calculator in English and Hindi; confirm the result is announced once;
  5. upload a document and review extracted values;
  6. property partition wizard.
  Check that the Hindi voice is used for `lang="hi"` names and for the Hindi UI, and that route
  changes announce the new heading.
- **Chart names in other scripts.** A tree node's accessible name is an `aria-label` string, which
  cannot carry `lang` for a Devanagari name inside it. The list view (`?view=list`) does carry it
  and is the recommended alternative. Confirm the chart experience with a screen reader.
- **Tooltips.** Privacy and evidence hints on badges are in `title` attributes only, so they are
  hover-only and not available to keyboard or touch users. The visible badge text carries the
  essential information; consider a disclosure for the longer hint.
- **Document alt text.** Image previews are named "Preview of ‹title›". For scans of text, the OCR
  tab is the text alternative. For photographs, consider a user-supplied description field.
- **Also not automated:**
  - Windows High Contrast / `forced-colors` (the chart's SVG fills are fixed colours; the status
    bars differ by shape, so they should survive);
  - text-spacing overrides (1.4.12);
  - session-expiry warnings (2.2.1);
  - review of the Hindi accessible names by a native speaker;
  - the mobile "More" button does not show when the current page is one of its items.

## How to run

```
make a11y                                 # = cd e2e && npx playwright test a11y
cd e2e && A11Y_VERBOSE=1 npx playwright test a11y   # print every violation (any impact) and "needs review" ids per page
```

The spec starts the backend and SPA itself, like the other E2E specs (see
`e2e/playwright.config.ts`). In CI it runs inside the existing `e2e` job, which runs every spec.
A serious or critical axe violation, a heading-outline break, or a failed keyboard or semantics
assertion fails the build, and the Playwright HTML report is uploaded on failure.

When adding a page, add it to `treePages()` in `e2e/tests/a11y.spec.ts`. When adding an
interaction pattern, add a keyboard-only script next to the existing ones.
